# Windows workstation setup and service cutover

Use the Windows 11 PC for local development first. The same PC can take over the live OptiLens service once it passes the rehearsal and can stay available to staff and workers through sign-out, sleep policy, and reboot. The app and its workers must run unattended under the service identity, independently of either desktop agent.

## 1. Verify the development setup

- Install or update the official Windows clients and sign in interactively. Open the same Git checkout in ChatGPT desktop’s Codex surface and in Claude Desktop’s Code tab. Use separate worktrees for concurrent edits. [OpenAI desktop app](https://help.openai.com/en/articles/20001276-moving-to-the-new-chatgpt-desktop-app) · [Claude Code desktop](https://code.claude.com/docs/en/desktop)
- Use a supported Node.js LTS release, Git for Windows, and the repository lockfile. Record the Node version that passes the rehearsal and use it for the service. [Node.js releases](https://nodejs.org/en/about/previous-releases)
- In each agent, confirm that the workspace is correct, that it loads `AGENTS.md`, and that it sees the project’s live-write boundaries. Claude imports the same file through `CLAUDE.md`. Start with default workspace-scoped access and review any additional permissions. [OpenAI project instructions](https://learn.chatgpt.com/docs/agent-configuration/agents-md) · [OpenAI Windows sandbox](https://learn.chatgpt.com/docs/windows/windows-sandbox) · [Claude project instructions](https://code.claude.com/docs/en/memory)
- In the development checkout, check `git status --short --branch`, then run `npm.cmd ci`, `npm.cmd run check`, and `npm.cmd test` from PowerShell. Calling `npm.cmd` directly works when PowerShell blocks `npm.ps1`. Keep live configuration and operational state in the service environment.

## 2. Keep the existing DNS service and site name

Move the Node service and its local Host Monitor together. Keep SQL Server, Technitium and its zone, and the existing DHCP configuration in place. The Host Monitor reads the local listener and runs local lifecycle scripts. Its current HTTPS & DNS controls assume that IIS and Technitium run on the same machine, so continue managing DNS and its CA on the existing server and verify the monitor’s local service and task views separately.

1. Record the current authoritative address, DNS TTL, and HTTPS binding in the private cutover record. Reserve a stable LAN address for the PC through the existing address-management process. Review static clients and any IPv6 record before changing the site address.
2. Prepare a server leaf certificate covering the existing OptiLens hostname and signed by the already trusted CA. Keep the CA private key on its current host. Provision the leaf and its protected private key on the PC through approved host-local configuration. Verify the new listener under the existing hostname against the PC’s address with a client-local DNS override before editing shared DNS. Use normal certificate validation.
3. In the approved window, change only the OptiLens address record to the PC’s address. Keep Technitium serving the zone and preserve its NS and SOA records. Verify the authoritative answer and the HTTPS health and sign-in paths from a staff device after the DNS TTL. For rollback, restore the recorded address and old service ownership, then recheck both endpoints after cache expiry.

## 3. Rehearse from an isolated service checkout

1. Record the source host’s Git commit and running application fingerprint, enabled workers and scheduled tasks, service identity, user-facing URL and TLS, databases and source connections, file routes, and queued work. The health endpoint reports the application fingerprint, and `git rev-parse --short HEAD` reports the checkout commit. Inventory local state by type and store the private details in approved host-local configuration. Follow the [remote operations runbook](REMOTE_AGENT_OPERATIONS.md) for any source-host inspection.
2. Use a separate service checkout with loopback binding, a provisioned test database with synthetic or appropriately sanitized data, and test folders and connector fixtures. Keep production credentials, outbound destinations, and production queues outside the rehearsal. Full-edition startup can initialize workers and recover RX processing, so a loopback listener alone provides no isolation. Explicitly configure the app, source, and reporting database targets before running any startup or database smoke command. The licensed-edition installer targets a fresh site and database.
3. Exercise sign-in, representative reads, and a synthetic workflow through its UI and authenticated API. Check `GET /api/health/live` for process and revision, and `GET /api/health` for required integrations. Rehearse unattended startup and reboot recovery before serving staff. Verify every actual required connector with a harmless read under the intended identity when access has been authorized.
4. Have both agents reproduce the same read-only flow. Start with the existing APIs and lifecycle commands. If they need a common MCP connector, expose narrow health and workflow-read operations first. Write tools must call the same authorized, audited application actions and respect confirmation and idempotency. Keep production credentials with the service and use connector or browser fixtures for actions involving patient or financial data. [OpenAI MCP](https://learn.chatgpt.com/docs/extend/mcp?surface=cli) · [Claude Code MCP](https://code.claude.com/docs/en/mcp)

## 4. Switch the website service in an agreed window

1. Keep the existing SQL databases and external source systems in place. Back up the app database and required file state and prove restore before switching. Inventory staging, archive, extension signing and TLS material, and any protected integration state actually in use. Reprovision user-scoped DPAPI credentials under the new service identity through the approved configuration path. Plan for fresh sign-in sessions.
2. Quiesce staff traffic and the old host’s application tasks, watchdog, and workers. Confirm in-flight jobs have completed or are accounted for. Start the new app and workers in a controlled order so only one host consumes production queues or processes business jobs. Update the address record in the existing Technitium zone when the PC is verified. Check callbacks and any routes outside the LAN separately.
3. Verify the running revision, authenticated access, connection health, and queue reconciliation. If the current host monitor is retained, run `node scripts/monitor-harness.js verify` on the new host. Verify staff access from another device and confirm service recovery after reboot. If a required check fails, fence the new host, reconcile changes made since cutover, and restore routing and worker ownership to the old host. Use a backup restore only after accounting for post-cutover transactions.
4. Retire old launchers, scheduled tasks, and host services once the replacement has proven startup, recovery, and rollback. Keep the Innovations, SQL, and file-drop contracts required for lab operations until each has a verified replacement. Maintain their compatibility inside the existing integration modules while exposing supported interfaces to both agents.
